# CKS-013 — Solution

Two policies, each a **ConstraintTemplate** (the reusable Rego) plus a
**Constraint** (where it applies).

## Apply order matters

A `Constraint` (e.g. `kind: K8sDenyPrivileged`) is a *custom resource* whose CRD
is generated by its `ConstraintTemplate`. If you apply the Constraint before its
CRD is established, you get `no matches for kind "K8sDenyPrivileged"`. So apply
templates first, wait for the CRDs, then apply the Constraints:

```bash
# 1. templates (these create the constraint CRDs)
kubectl apply -f solution/01-template-deny-privileged.yaml
kubectl apply -f solution/03-template-required-labels.yaml

# 2. wait for the generated CRDs to be established
kubectl wait --for condition=established --timeout=60s \
  crd/k8sdenyprivileged.constraints.gatekeeper.sh \
  crd/k8srequiredlabels.constraints.gatekeeper.sh

# 3. constraints
kubectl apply -f solution/02-constraint-deny-privileged.yaml
kubectl apply -f solution/04-constraint-require-owner-label.yaml
```

Applying the whole directory in one shot also works if you run it **twice** —
the first pass creates the templates, the second binds the Constraints once the
CRDs exist:

```bash
kubectl apply -f solution/   # templates land; constraints race and error — expected
kubectl apply -f solution/   # CRDs now established; constraints bind
```

## Why each piece is needed

| Object | Kind | Purpose |
| --- | --- | --- |
| `k8sdenyprivileged` | ConstraintTemplate | Rego that flags any container/initContainer with `securityContext.privileged: true`. |
| `deny-privileged` | K8sDenyPrivileged (Constraint) | Applies the rule to all Pods **except** `kube-system` via `match.excludedNamespaces`. |
| `k8srequiredlabels` | ConstraintTemplate | Rego that flags a missing label, with the key(s) supplied as a **parameter** (`input.parameters.labels`) — not hard-coded. |
| `require-owner-label` | K8sRequiredLabels (Constraint) | Scopes to `app` + `staging` via `match.namespaces` and passes `parameters.labels: [owner]`. |

## The traps

1. **Template ≠ enforcement.** A ConstraintTemplate alone enforces nothing — it
   only *defines* a kind. The Constraint is what turns it on and says where.
2. **Scope with the Constraint, not the Rego.** Keep the Rego generic; use
   `match.namespaces` (opt-in) and `match.excludedNamespaces` (carve-out) on the
   Constraint. That is why the privileged rule can be cluster-wide-minus-kube-system
   while the label rule is limited to two namespaces, with one template each.
3. **Propagation delay.** After a Constraint is created the webhook takes a few
   seconds to start enforcing it. Retry your test pods rather than trusting the
   first result.
4. **Admission control is forward-looking.** The pre-existing `legacy-app` pod is
   not evicted — Gatekeeper only vets *new* admission requests. Delete/replace it
   to bring it into compliance.

## Verify by hand

```bash
# rejected (privileged, even with an owner label):
kubectl -n app run bad1 --image=registry.k8s.io/pause:3.9 --labels=owner=me \
  --overrides='{"spec":{"containers":[{"name":"c","image":"registry.k8s.io/pause:3.9","securityContext":{"privileged":true}}]}}' \
  --dry-run=server
# rejected (no owner label):
kubectl -n app run bad2 --image=registry.k8s.io/pause:3.9 --dry-run=server
# admitted (compliant):
kubectl -n app run good --image=registry.k8s.io/pause:3.9 --labels=owner=me --dry-run=server
# admitted (privileged but in the excluded namespace):
kubectl -n kube-system run ok --image=registry.k8s.io/pause:3.9 \
  --overrides='{"spec":{"containers":[{"name":"c","image":"registry.k8s.io/pause:3.9","securityContext":{"privileged":true}}]}}' \
  --dry-run=server
```
